06 / ABSTRACTION REVIEW

抽象审查：概念是否沿着变化的边界切开

这里讨论的不是待修 bug，而是系统变化时，现有概念还能不能各负其责。「当前概念」沿用本文已有源码依据；变化场景是假设，候选边界是取舍，均不代表已批准的重构。

01 / Session 与运行时：保存了什么，谁仍然活着

当前概念：Session 是 UUID 磁盘快照与恢复载体；运行中状态分散在 App 和 managers，build_snapshot 汇总多域。恢复记录不等于恢复执行。

混杂的职责：「会话」同时指历史身份、持久化数据和活跃工作的归属；这几种寿命不同，快照 DTO 不能自然成为运行时聚合根。

变化场景如何暴露边界：若会话要脱离 TUI 持续运行，再由另一宿主接管，就必须回答谁拥有任务、谁负责停机、从谁读取一致的快照；增加序列化字段不能回答这些问题。

候选边界与取舍：保留 SessionSnapshot 作为持久化协议，考虑让 SessionRuntime 协调生命周期与状态。收益是宿主可替换，代价是所有权迁移与恢复协议复杂度；若始终单宿主前台运行，可先明确命名和快照契约，不急于新增聚合根。

需用户决定：会话是可恢复的工作记录，还是跨宿主持续存在的执行实体？是否真的需要脱离 UI 的持续运行？

02 / Turn / Operation / Task / Agent：不是四种拼法的「任务」

当前概念：TurnRunner 编排模型与工具回合；OperationId 标记事件归属与取消所有权；TaskManager 管 pipe / PTY 进程；AgentManager 管带独立对话的模型工作，并共享父级部分资源。

混杂的职责：用户目标、调度单位、取消范围和执行载体容易都被称为任务。但进程可活得比模型流更久，独立对话也不意味着独立资源权限。

变化场景如何暴露边界：停止前台回合但保留构建进程，与取消整组委派工作，是两个不同动作；不能靠一个通用 cancelled 状态推导所有后代资源的处置。

候选边界与取舍：保留四个概念，显式描述父子关系、资源归属与取消传播；必要时增加监督层，而非合并成万能任务框架。代价是多套类型与转换，收益是不会把进程退出误当成用户目标完成。

需用户决定：停止回合默认保留哪些后台工作？子代理完成由最终回复、工具结束还是父级验收定义？重启后仅展示记录，还是承诺续跑？

03 / App / Runner / 宿主：交互策略在哪里结束

当前概念：Runner 复用模型—工具编排，AgentSurface 提供事件和审批端口；App 同时装配 TUI、协调状态、调度和恢复。Runner 还包含记忆关联、诊断和项目文档提醒等产品职责。

混杂的职责：核心执行、产品工作流和宿主交互条件不总沿同一边界变化。移进 Runner 不自动意味着宿主无关，全部留在 App 又会让其他入口重复定义行为。

变化场景如何暴露边界：新增服务端或可重连客户端时，审批等待、用户草稿阻塞和压缩触发方式会变化，但工具执行结果仍应保持可解释。共享执行代码不等于所有入口必须功能完全对等。

候选边界与取舍：保留 AgentSurface，显式输入宿主能力与阻塞条件，由应用服务或 hooks 组合产品工作流。收益是独立测试与复用，代价是端口和配置面增加；若只服务 TUI，先明确入口差异比预造通用宿主框架划算。

需用户决定：TUI、headless 与未来宿主要保证哪些行为等价，哪些允许不同？审批和长任务是否要在断线后继续等待？

04 / Conversation / MessageItem / 投影：历史不只是 API 输入

当前概念：Conversation 持有无 UI 的历史、usage、压缩边界和 API 输入投影；MessageItem 使用 Responses 类型，也承载 UI-only peer 记录；PartialResponse 维护流状态与展示 revision。

混杂的职责：提供商协议记录、用户时间线、模型上下文与渲染缓存共用相邻数据结构。没有 UI 组件依赖，不等于消息模型已经与协议和展示语义解耦。

变化场景如何暴露边界：增加非 Responses 后端、改变 peer 展示或导出完整审计时，必须分别决定哪些记录能发送、哪些须保留、哪些仅影响渲染；压缩后的模型上下文并不是全部历史。

候选边界与取舍：先明确历史记录、模型输入与 UI 投影的转换规则；多协议需求成立后再考虑稳定的内部对话事件与 provider adapter。收益是变化隔离，代价是映射、迁移和协议细节保留的复杂度，不必立刻引入完整事件溯源。

需用户决定：历史应保留原始提供商响应，还是只保证用户可见内容可恢复？多协议支持和审计完整性是否是近期要求？

05 / Tool / 审批 / 资源授权：同意意图不等于授予能力

当前概念：ToolRegistry 管 schema、路由和执行；Classifier 按模式判断 Allow / Deny / Ask，AgentSurface 接收人工审批；SecurityHandle 约束路径、读取快照和进程沙箱。Yolo 放行分类不代表关闭沙箱。

混杂的职责：工具是否可发现、调用是否符合工作意图、具体资源操作是否获准，是三个问题。统称权限，会让调用批准被误解成持续授权，也让能力元数据被误当最终安全保证。

变化场景如何暴露边界：同一工具由 Runner、子代理或 MCP server 调用时，审批入口可以不同，但资源约束仍须明确；父级批准一次调用能否被共享资源的子代理复用，不能由共享句柄偶然决定。

候选边界与取舍：保持调用审批与资源授权分层，明确许可主体、操作、资源、有效期和传播范围；能力声明用于发现和调度，不代替执行时授权。收益是可审计，代价是授权上下文和交互更复杂，不建议合并成一个万能 allow 布尔值。

需用户决定：一次批准只放行该调用，还是允许会话内同类操作？子代理继承哪些许可、哪些必须再请求？各入口要共享怎样的安全基线？

06 / Checkpoint / rewind：撤销的是哪一个世界

当前概念：Checkpoint 保存 prompt 级对话 cutoff、todos 和已记录的内置文件编辑 before/after；它独立于 Session 持久化。恢复先检查 after hash 冲突，再逐文件写回，不覆盖全部 shell 或 MCP 副作用。

混杂的职责：回退同时暗示对话分支、待办恢复、文件撤销乃至执行世界回到过去；这些载体和责任不同，不能因为共用一个按钮就成为同一事务。

变化场景如何暴露边界：一轮同时编辑文件、启动进程和调用远端服务后，rewind 如何说明残留影响？恢复中退出或用户已手改文件时，问题不仅是异常处理，更是允许什么部分完成、谁决定继续。

候选边界与取舍：优先限定为「对话回退 + 已记录本地编辑恢复」，显式展示范围、冲突和不可撤销影响；更强需求再考虑恢复计划、日志与补偿协议。后者增加可恢复性，但成本高，本地事务也无法消除任意外部副作用。

需用户决定：rewind 默认只改对话还是同时还原文件？有冲突或不可撤销影响时，拒绝整次请求、允许部分恢复，还是逐项确认？产品承诺到哪一层？

07 / POSSIBLE FUTURES

不要把架构审美伪装成唯一答案

我的偏好是先收拢运行时所有权，再考虑物理拆包。下面是三个真实可选的范围，不是三个都要做。

A · 推荐起点

修契约，不搬家

保留单 crate 和现有宿主。修复经过验证的失败语义，建立关键不变量。

  • 调用原序与审批结果分离
  • 终止 / 成功 / 取消明确区分
  • 恢复失败保留可恢复信息
  • agent 终态监督与委派 claim 恢复

收益：风险最低，回归范围可控。
代价：App 的协调复杂度仍然存在。

B · 中期候选

提取 SessionRuntime

让业务运行时拥有 Conversation、调度和后台工作；App 只做宿主装配与 UI 投影。

  • 调度输入用显式 HostBlockers
  • todo 单一写入源 + revision 快照
  • 运行期事件独立于 ui::event
  • 统一 RunOutcome 与终态提交点

收益：无终端测试与多宿主复用更直接。
代价：所有权迁移影响事件、保存和恢复链路。

C · 暂缓

多 crate / 插件内核

把 kernel、工具、存储与终端适配器变成物理编译边界。

  • 更严格的依赖约束
  • 可独立复用的执行内核
  • 端口、DTO 和版本边界增加
  • 不能自动解决崩溃一致性

适用：确有嵌入式 API / 多前端演化需求。
代价：最高，不应仅为“看着干净”。

建议迁移顺序与验收条件

01 / 锁行为

写故障注入测试：混合工具审批次序、Failed/Incomplete、rewind 中途写失败、agent panic、委派 claim 后退出。
验收：先证明风险是否成立，不用“顺手重构”掩盖语义变化。

02 / 修失败

明确终态结果和恢复资产的保留规则，先做小范围补丁。
验收：取消不伪装成功，部分恢复不伪装无变化，持久化失败可见。

03 / 收所有权

以 todo 或前台 lifecycle 为小切口，让 UI 持快照，运行时持状态。
验收：业务测试无需创建 Ratatui 组件；旧行为不变。

04 / 再复用

比较 TUI / Headless / MCP 的能力差异，只统一相同策略和装配规则。
验收：交互差异保留，安全授权不因抽象统一而被放宽。
